## Commands

```bash
make install      # install dependencies via uv sync
make run          # install + run the game (uv run python -m src)
make train        # train the PPO agent (make train ITERS=500 to set iterations)
make curriculum   # train with the difficulty-ramp curriculum (make curriculum PROMOTE=0.8)
make resume       # continue training the last checkpoint (make resume ITERS=300)
make curriculum-resume  # resume a curriculum run (restores the stage reached)
make alphazero    # train the AlphaZero (PUCT self-play) agent on the curriculum
make alphazero-resume   # resume an AlphaZero run (restores the stage reached)
make play         # watch the trained policy play
make clean        # remove __pycache__, build artifacts

uv run python -m src                                    # run the game directly
uv run --extra ai python -m src.ai.train               # train PPO (see src/ai/)
uv run --extra ai python -m src.ai.train --resume      # continue from checkpoint
uv run --extra ai python -m src.ai.az_train --curriculum  # train AlphaZero
uv run --extra ai python -m src.ai.play                # watch the trained policy
```

Dependencies are managed with `uv` and locked in `uv.lock`. The project uses a `.venv` local virtual environment. The PPO agent lives behind the optional `ai` dependency group (`torch`), installed with `uv sync --extra ai` (the `make train`/`make play` targets do this for you). There are no tests yet; `pytest` is listed as a dev dependency for future use.

## Architecture

This is a pygame turn-based isometric grid game. The player tries to survive on a diamond-shaped map while Bolgrot (the boss enemy) and flame tiles threaten them. Each turn lasts 120 seconds; at the end of a turn, a new flame spawn pattern is placed on the map.

### Module responsibilities

- `src/game.py` — `Game` class: owns all game state and exposes both the interactive action API (`select_spell`, `play_selected_spell`, `clear_previsu`, `end_turn`, `reset`) and the **RL environment API** (`get_observation`, `legal_actions`, `step`, plus the `ACTIONS` table and the `observation_size()`/`num_actions()` static helpers). **No pygame dependency in its own logic** — it can be imported and driven headlessly (set `SDL_VIDEODRIVER=dummy` since it transitively imports pygame via `case`/`spells`).
- `src/renderer.py` — `Renderer` class: holds rendering state (screen offset, end-turn button, spell render list). All drawing methods receive game state as arguments and never mutate it. `_compute_map_offset()` (static method) calculates the isometric origin that centers the map on screen.
- `src/__main__.py` — pygame event loop only. Translates user input into `Game` method calls; passes game state to `Renderer` methods. Keyboard: `SPACE` ends the turn; `1`/`2`/`3` select the player's spell at index 0/1/2 (via `game.select_spell(event.key - pygame.K_1)`); `ESC` quits.
- `src/constant.py` — all magic numbers including layout constants (`RIGHT_PANEL_W`, `BUTTON_W`, `BUTTON_H`, `SPELL_GAP`) and map config path (`MAP_CONF`).
- `src/actions.py` — stateless click/hover helpers: `on_previsu_click()`, `on_spell_hover()`, `on_button_end_turn_click()`.
- `src/BFS/bfs.py` — `BFS` class: 4-directional breadth-first pathfinding over `Map.cases` (walls excluded). `find_path(start, goal)` returns the **single next step** toward the goal (one coordinate tuple) or `None`. Each `Spells` instance holds a `BFS` (assigned in `Game.__init__`); used as the fallback movement when the greedy quadrant step is blocked.
- `src/case/case.py` — `Case` class (grid cell with `x`, `y`, `entity`, `case_type`) and `CaseType` enum (`FREE`, `WALL`, `EMPTY`). `Case.draw()` handles isometric rendering and `Case.contains()` does mouse hit-testing.
- `src/button/button.py` — `Button` class for the end-turn button.

### Map representation

`Map.cases` is a `dict[tuple[int, int], Case]` keyed by `(x, y)` — lookups (`Map.place_entity`, `Spells._find_case`, `BFS.is_valid_position`) are O(1) `cases.get(pos)`. Iterate values with `for case in cases.values()`. Each `Case` holds its grid coordinates (`x`, `y`), an optional `entity: Entity | None`, and a `case_type: CaseType`.

The map is loaded from the packaged `src/config/bolgrot.map` (path in `constant.MAP_CONF`) by `Map.parse_map()`. The file uses a symbol grid: `.` = FREE, `#` = WALL, `|` = EMPTY, `N` = skip (no cell). After parsing, `self.grid_max_x` and `self.grid_max_y` store the bounds.

### Packaging & resource paths

`src` is a regular package (`src/__init__.py`). Data files (`src/config/*.map`, `src/sprites_png/*.png`) are declared as `[tool.setuptools.package-data]` and resolved at runtime via `importlib.resources.files("src") / ...` in `constant.MAP_CONF` and `constant.SPRITES_DIR` — so they work regardless of the current working directory (not just from the repo root). The game has a console-script entry point `bolgrot = "src.__main__:main"`; `__main__.py` exposes `main()` (called both by the entry point and the `if __name__ == "__main__"` guard for `python -m src`).

### Coordinate system

Iso conversion is done inline wherever needed:
- `iso_x = (x - y) * (CASE_WIDTH / 2)`
- `iso_y = (x + y) * (CASE_HEIGHT / 2)`

All rendering uses `offset: tuple[int, int]` — the screen pixel position of iso origin (0,0), stored on the `Renderer` instance. The inverse (mouse → grid) is computed in `Case.contains()` and in `on_previsu_click()` in `actions.py`.

### Entity hierarchy

```
Entity (ABC)
├── blocks_sight: bool = True   (Player overrides to False)
├── killable: bool = True        (Bolgrot overrides to False)
├── Player   — pos_x/y, hp, base_PA, pa (current AP), list[Spells]
├── Bolgrot  — pos_x/y, killable=False
└── Flame    — pos_x/y
```

### Spell system

```
Spells (ABC)
├── ShortJump  ("Astral leap")  — LINE range 1, implemented play()
├── LongJump   ("Double leap")  — LINE range 2, implemented play(), tracks time_used
└── MoveFlames ("Inaction")     — DIAGONAL range 1, line_of_sight=False, attracts all flames toward the player
```

The `Spells.__init__` signature takes a `bfs: BFS` argument (after `type_spell`, before `line_of_sight`). `Game.__init__` builds one `BFS(self.map)` and assigns it to every spell.

Each spell defines `type_spell: list[tuple[TypeSpell, int]]` where `TypeSpell` is LINE/DIAGONAL/FULL and the int is range. `Spells.previsu()` computes reachable tiles using `is_in_map()`, `is_blocked_by_sight()`, and `is_entity_killable()` — line-of-sight IS enforced in `previsu()` via the `line_of_sight` bool. All three concrete spells have implemented `play()` methods.

Spells also carry `cost` (AP cost), `max_use`, `time_used` (base-class attr, default 0), `effects: list[str]`, and render a tooltip on hover via `_draw_tooltip()`. `Spells.is_castable(player)` returns `player.pa >= cost and time_used < max_use`. `Game.select_spell()` calls it first and refuses to build a previsualisation (clearing it) for an uncastable spell, so out-of-AP / maxed-out spells can't be selected, hovered into a previsu, or cast.

**Flame attraction** (`Spells.attract_flames`, shared by all three spells' `play()`): flames are sorted nearest-first (Manhattan) and each moves **one** tile toward the player along the axis of greatest distance — `|dx|>|dy|` steps in x, `|dy|>|dx|` steps in y, equal steps diagonally. This keeps each flame inside its quadrant relative to the player. If the chosen tile is a WALL or off-map, it falls back to `BFS.find_path`. A flame landing **on the player** sets `player.hp = 0` (only when `killable`); a tile already holding **another flame or Bolgrot blocks the move** (flame stays put) and does **not** kill. Attraction kills *only* by reaching the player — flame-on-flame during attraction is not lethal (unlike pushback, below).

**Flame pushback** (`Spells.push_flames`): the counterpart to attraction, run by `ShortJump`/`LongJump` `play()` **only after a flame is killed** and **before** `attract_flames`. It takes the flames **adjacent** to the player (Chebyshev distance ≤ 1, diagonals included) and steps each **one tile away** along its dominant axis (same axis/`sign` logic as attraction, WALL/off-map falling back to `BFS.find_path`). A pushed flame landing on **another flame or the player** sets `player.hp = 0`; Bolgrot blocks (flame stays). **Diagonal pushes are extra-lethal**: when a flame is pushed diagonally (from `(x, y)` to `(x+sx, y+sy)`), a flame on **either orthogonal flank it squeezes between** — `(x+sx, y)` or `(x, y+sy)` — *also* kills, not just one on the destination `(x+sx, y+sy)`. (E.g. a flame at `(4,4)` pushed to `(5,5)` dies against a flame at `(5,5)`, `(5,4)`, **or** `(4,5)`.) This is intended base-game behaviour — chaining a flame into another flame is a real way to die, not a bug. Net effect when you land on a flame: adjacent flames are pushed out one tile, then `attract_flames` pulls *all* flames (adjacent and not) back one tile, so only the non-adjacent ones make net progress toward you.

**Dependency layering (acyclic).** Imports form a clean DAG: `constant` → `entity` → `case`/`map` → `BFS` → `spells` → `game`. `Player` is spell-agnostic — it holds `self.spells: list[Spells]` (empty by default; the `Spells` type is a `TYPE_CHECKING`-only import) and does **not** import `spells` or `BFS`. `Game.__init__` constructs the concrete spells (`ShortJump`/`LongJump`/`MoveFlames`) with a shared `BFS(self.map)` and assigns them to `player.spells`. Because `entity` no longer depends on the higher layers, every module imports cleanly regardless of entry point; `spells` modules import entity/case classes normally at module top level.

### Flame spawn patterns

`Patterns(seed=None)` holds `_all_patterns` (class-level list of patterns); each pattern is a list of grid coordinates. `Patterns.draw()` picks one at random (without replacement) using a seeded `random.Random` instance, making runs reproducible. Each turn, the drawn pattern is passed to `Game.end_turn()` which calls `Map.place_entity()` per position. `Patterns.reset()` restores the full pool.

### Sprite assets

Sprites are stored as both `.xcf` (GIMP source) and `.png` in `src/sprites_png/`. Spell classes reference `.png` filenames in their `sprite` field. Images are lazy-loaded on first access via the `image` property.

### RL environment / PPO agent

`src/ai/` (optional `ai` dependency group, `torch`) trains a **PPO** agent to play the game headlessly. It drives `Game` purely through the environment API below — no game logic lives in `src/ai/`.

**Winnability / the flame-clear mechanic (read this before tuning rewards).** The mechanics are the finished base game and are **fixed** — the goal is a policy that beats the game *as-is*, not a reward hack or a mechanic change. Why it's hard: a flame is removed **only by jumping onto its tile**; every jump also runs `push_flames` (adjacent flames shoved out one tile, and a flame chained onto another flame or the player is instant death) then `attract_flames`, dragging *all* other flames one tile toward the player, and a flame reaching the player is instant death. So clearing flames greedily is self-defeating — measured random-search win rates: 1 flame ~11%, 2 ~2%, 3 ~0.3%, a full 6-flame wave **0%**, and the full 6-wave game **0%** (32k games, min 32 flames left). Random/naive play essentially never wins, so `REWARD_WIN` is (almost) never hit by an untrained policy — but this is a **skill / exploration** problem, not an unreachable-goal one: reward-weight tuning alone won't manufacture a winner, and the curriculum (below) exists to bootstrap the policy from trivially-winnable shrunk games up to the full game rather than to sidestep an impossible task.

**Empirically confirmed (2026-07).** With the curriculum plus the fixes it took to make it learn (`--ent-coef 0.03` to break a position-blind canned-action collapse, `--lr-floor 0.1` so each session keeps learning instead of freezing when the LR anneals, and chained short `--resume` sessions), PPO trained **all the way from stage 0 up to the full game (stage 7/7)**, winning up to ~65% on the shrunk winnable stages — and *still* **0%** on the full 6-wave game. So a **competent trained agent** (not just random search) reconfirms the wall: *reaching* the full game is a solved training problem, *winning* it is not, absent a mechanic change. The trained policy plays it "as well as the mechanic allows" (`approach` reward strongly positive — it actively hunts flames — clearing a few before an attracted flame kills it).

**Overturned — the full game IS winnable (2026-07, via search).** The 0% above is a limit of *model-free* PPO, **not of the game**: PPO can only reinforce wins it randomly stumbles into, and the winning line is far too deep (~60 actions) for random exploration to ever hit. A **planning agent that does explicit lookahead on the deterministic model wins the full 6-wave game** (not every seed, but PPO never wins any) — `src/ai/mcts.py` (MCTS) clears the flames and triggers `REWARD_WIN` on the true patterns: **50% win rate over 6 full-game seeds** at 300 sims/move (`clear ≈ +318`, `terminal ≈ +45`), versus **0%** for the trained PPO policy *and* every scripted baseline (`python -m src.ai.baselines --mcts-sims 300 --seeds 6`). So the binding constraint was the **algorithm class** (model-free vs planning), never the mechanic. Treat the "mechanic wall" language above as *PPO's* wall; the mechanic itself has winning lines a search agent finds.

**MCTS is nowhere near 100%, and more search does not help (2026-07-10).** The 50% above is the *current*, honest number. This line previously read 83% — measured at commit `3139b49`, **before** `e539de7` ("fixed bug on push flame") made a diagonal push lethal against a flame on either orthogonal flank. The old 83% was **inflated by a bug the search had learned to exploit**: with the flanks non-lethal, MCTS could chain flames diagonally past other flames for free, a line no human would play. Closing the hole cost it 5/6 → 3/6, and that drop is *correct* — the search was cashing in an illegal escape, not playing well. Two lessons. **A planning agent will find and exploit any mechanic bug**, so an unexpectedly high MCTS win rate is evidence to audit the mechanic, not to celebrate. And **every win rate in this file must be re-measured after any flame-mechanic change** — these numbers are only meaningful against a fixed ruleset. Two sweeps (12 games each, `EVAL_SEEDS[:6]`) show the 40-50% plateau is insensitive to search budget: **300 → 600 sims/move changes nothing**, and **`rollout_depth` 16 → 32 → 64 changes nothing** (2/6, 2/6, 3/6), even though depth 64 covers the whole ~60-action winning line. Aggregating 30 games across every config, each of the 6 seeds is won by *some* run (12/30 ≈ 40% overall), so no seed is unwinnable — which flame the search saves is decided by the rollout RNG. A plateau insensitive to both budget and horizon points at the **leaf-value quality**, not the search: `safe_greedy` rollouts are too noisy for the backup to discriminate branches, and more/longer rollouts only refine a biased estimate. That is exactly what `alphazero.py`'s learned value head is meant to replace — but see its Status below.

**Phase 2 — AlphaZero (PUCT self-play), implemented (2026-07).** MCTS wins but is slow (2-5 min/full game at 300 sims/move, measured 2026-07-10 — it rebuilds a tree with rollouts every move; longer games are the *winning* ones, ~65 plies). `src/ai/alphazero.py` is the planned AlphaZero upgrade: it reuses `network.py`'s `ActorCritic` inside a **PUCT** search — the policy head supplies the prior `P(a)` that weights exploration, and the **value head replaces the rollout** (one leaf eval instead of simulating to the end). A **self-play** loop trains the net on the search's own visit distributions (policy target) and the games' discounted shaped return-to-go (value target), so the fast reactive net is bootstrapped toward MCTS strength. Two carry-overs the game forces (same as `mcts.py`): the value target is the **shaped return** (wins too deep for a win/loss leaf), and because that return is large/unbounded PUCT normalises `Q` with a running min/max (MuZero's trick) so `c_puct` is scale-free; and self-play runs on the **same curriculum ramp** (an untrained value head is noise on the full game, exactly PPO's wall).

**AlphaZero results so far (2026-07-10).** A cold run (100 iters, 8 games/iter, 80 sims/move, `--curriculum`) climbed the whole ramp in **70 iterations** and **won the full game** — `eval_win 6.2%` (1/16) at iteration 95, `eval_reward` ~81. That is the **first trained agent ever to win this game**: PPO scores 0% and returns **-25.19**; AlphaZero returns +30 to +160 on the full game because it clears ~10 flames before dying (MCTS clears ~32, `clear ≈ +318`). Two findings from that run. (1) **The ramp's only real wall is the 2-flame stage** `(1,2,1)` — 30 iterations, versus 5-10 for every other stage including all the extra-wave ones. Adding a *wave* is nearly free for a search agent; adding a *flame* is not. The stage ordering (by `greedy_clear` ceiling) does not reflect AlphaZero's difficulty. (2) **A `--resume` at 80 sims plateaued**: 20 evals, `eval_reward` 120-160, `eval_win` **0%**, and `selfplay_win` **0% across 640 consecutive self-play games**. With no win in the buffer the policy target never sees a winning line and the value head only fits losing shaped returns — the agent optimises "die late", which is what shaping measures. The fix is not reward tuning (see the box above; `REWARD_*` changes force a full retrain and cannot manufacture a line the search never finds). Raising self-play to `--simulations 300` and adding the `line` bridge stage **halved the ramp's cost** (2-flame wall 30→15 iters; full game reached at iter 60 not 70) but on their own did **not** move the ceiling (still 6.2%, still `selfplay_win 0%`), because more iterations alone cannot help while no win reaches the buffer: shaped reward pays for clearing/approaching flames, winning needs *all 36 cleared without dying once*, so a policy gets better at farming reward and no better at finishing (the 80-sim resume ran 85 extra last-stage iters and `eval_win` went 6.2% → 0% while `eval_reward` climbed 32 → 160). Two changes broke that: **`--bootstrap-games`** puts MCTS wins in the buffer to imitate, and the **`VALUE_SCALE`** fix (see the equal-budget box below) un-crushed the policy head. Together they took full-game `selfplay_win` from 0% to 37.5% and the equal-budget win rate from 0/6 to 1/6.

**AlphaZero now wins the full game at equal search budget (2026-07-10), after a value-scale fix.** `baselines --az src/ai/az.pt --az-sims 300 --mcts-sims 300 --seeds 6`, same seeds and sims/move — the middle row is the earlier undertrained net, kept to show the jump:

| policy | return | win% | steps | clear | terminal |
|---|---|---|---|---|---|
| mcts | 374.83 | **50.0** | 56.0 | 318.33 | +45.00 |
| alphazero (fixed) | 211.31 | **16.7** | 44.5 | 208.33 | +2.50 |
| alphazero (pre-fix) | 92.25 | 0.0 | 37.5 | 120.00 | -15.00 |
| trained (PPO) | -25.19 | 0.0 | 16.7 | 6.67 | -29.17 |

AlphaZero is now a clear #2 that *wins* (1/6, up from 0/6): +88 flames cleared, +7 plies survived, `terminal` back positive. MCTS still leads (3/6) — but it is at a fixed ceiling with per-move rollouts, while this net keeps improving and evaluates a leaf with one forward pass. **The earlier 0/6 was not a PUCT-vs-UCB1 gap; it was a training bug.** The value target is the shaped return (O(100)); its MSE (O(10^4)) dominated the O(1) policy cross-entropy through the shared trunk and the global grad clip, so the **policy head never left its uniform init** (measured: prior entropy within 1% of uniform, `p_loss` flat all run). With a uniform prior, PUCT has no guidance and degenerates toward whatever the value head likes — high immediate `clear` — which is exactly the "clears 12, dies early" behaviour above. The fix is `VALUE_SCALE` (below): normalise the value target so both losses are O(1). After it, `p_loss` fell for the first time, the prior sharpened, the `line` stage went from *never promoting in 65 iters* to *93.8% on the first eval*, and full-game `selfplay_win` — 0% in every prior run — reached **37.5%**, i.e. the self-play loop finally generates its own winning lines. All three of the session's changes were needed (`line` stage, MCTS bootstrap, value normalisation); normalisation was the decisive one.

**Two caveats on the above.** Six seeds make 1/6-vs-3/6 a coarse read, and the run stopped at 100 iters with `p_loss` still falling and `selfplay_win` still climbing — it had not converged, so a `--resume` should push it further. The per-iteration `eval_win` in the training log stays noisy and *understates* the net badly, because it evaluates at 120 sims while the net is much stronger at 300 (on the `line` stage: 2/16 at 120 vs 16/16 at 300). Judge AZ by the equal-budget `baselines` table, not the training-log `eval_win`.

**A `--resume` closed the gap: the 64-net now equals MCTS (2026-07-11).** The uncoverged 100-iter net above was pushed with more `--resume` sessions (same recipe: `--simulations 300 --bootstrap-games 8`) and reached **3/6 (50%) at equal budget — a dead heat with MCTS** (`baselines --az src/ai/az.pt --az-sims 300 --mcts-sims 300 --seeds 6`: AZ return 358 vs 374, clear 305 vs 318, both `terminal +45`, survives 56.8 vs 56 plies). First *trained* agent to match the planning search at equal budget. But that is the ceiling: **further `--resume` of the same recipe stopped helping** — an iter-225→325 session left `az.pt` unrewritten (best 37.5% eval@120 never beaten), `p_loss` flat 1.66→1.63, no benchmark gain. AZ = MCTS = ~50% is a hard plateau for this recipe.

**Network capacity is NOT the plateau — it is the reward shaping / leaf-value ceiling (2026-07-12).** Tested `--hidden 128` (double the default 64 width; needs a cold restart — width is baked into checkpoints). A cold h128 (300 sims, bootstrap 8, 100 iters) climbed the ramp fast (2-flame wall in ~5 iters, `line` 93.8%, full game by iter 55) and — unlike the 64-net — its *self-play* began winning the full game (`selfplay_win` 12.5-50% vs 64-net's 0%), a real new signal that capacity unlocked something. But at equal budget the **converged** h128 does **not** beat the 64-net: benchmarked at 300 sims across three snapshots — cold **2/6**, iter-200 `--resume` **3/6** (matches 64-net and MCTS), iter-300 `--resume` back down to **1/6** (clears just as much, `clear` 298, survives 52.7 plies, but `terminal` +7.5 vs +44 — it learned to "die late clearing more", not to finish). So h128 oscillates in the same **1-3/6 = MCTS-50% band** as the 64-net, and 100 extra iters (200→300) *regressed* the win rate while `p_loss` still fell 1.65→1.59 — the "more iterations don't help" wall, now reconfirmed at double capacity. **Verdict: two independent widths converge to MCTS's ~50% ceiling, so the binding constraint is the shaped-reward value target / leaf-value quality, not network size.** More width, more iterations, and more bootstrap (capped at MCTS's ~50% teacher) all leave the ceiling at 50%. Breaking it needs a *different* leaf-value signal (a win/loss-aware target, a stronger search than MCTS to bootstrap from, or a reward redesign — all full retrains), not a bigger net. (h128 artefacts live in `tmp/`: `az_h128_iter200_3of6.pt` is the best h128 snapshot; `src/ai/az.pt` — the 64-net 3/6 — remains the canonical best.)

**Attacking the leaf-value ceiling: the `--value-target` A/B (2026-07-13).** Since the plateau is the value signal, `alphazero.py` gained a `--value-target {shaped,winloss,blend,twohead}` flag (threaded through the search, self-play, bootstrap and — for a coherent eval — `baselines --az-value-mode`). `shaped` is byte-for-byte the old recipe (dense discounted shaped return; the flame-count predictor that plateaus at 50%). The alternatives target the *ranking* failure "clears 32 then dies ≈ wins":
- **`winloss` — tried, failed (2026-07-13).** Value target and search backup become the discounted *game outcome* only (±1 terminal, 0 elsewhere): the canonical AlphaZero signal, so the head learns P(win) and PUCT ranks on it. It **climbs the curriculum fine but collapses on the full game**: self-play never wins there, so every full-game target is −1, the value head confidently predicts "all lost" (`v_loss` *falls* to 0.29), and with the dense shaped guidance gone the search has **no gradient to find flames** and degenerates to passing turns — measured `stall −480`, `clear +15`, `selfplay_win 0% for 26 straight iters`, `eval_win 0%`, and getting *worse* over time. The lesson: this game needs the **dense** shaping for exploration; a sparse outcome signal removes exactly what lets the search find the winning line (same reason PPO can't win). Do not pursue pure outcome targets.
- **`blend` — tried, failed (2026-07-13).** Keeps the dense shaped reward (search still explores toward flames) **and** adds a large terminal `±BLEND_TERMINAL_BONUS` (300, sized above the ~360 clear-count spread) to both the search edges and the *single* value target, so a win outranks the best near-win. Cold 64-net run at the proven recipe (`--simulations 300 --bootstrap-games 8 --iterations 100`). **Qualitatively it worked — quantitatively it did not.** It *avoided* winloss's collapse (stage-8 evals: `stall` stayed modest −15 to −73, `clear ~75-112`, and self-play *won the full game* ~12.5% sporadically, vs winloss's flat 0%). But at equal budget it scored **0/6** (`baselines --az src/ai/az_blend.pt --az-sims 300 --az-value-mode blend --mcts-sims 300 --seeds 6`: gate pick `clear 93`, final ckpt `clear 62`, both 0 wins) — *worse* than shaped's 3/6. Diagnosis: folding the ±300 terminal spike into the **single** shaped value target poisons the value estimate near a terminal (a state one avoidable-death away is dragged toward −300·γ), so the net learns to *avoid death* without learning to *finish*, and clears fewer flames than plain shaped. The terminal bonus and the dense estimate cannot share one head.
- **`twohead` — the fix, running (2026-07-13).** Splits the value into two heads (`value_dim=2`): head 0 regresses the **clean** shaped return (no terminal spike, so the dense exploration estimate is undistorted), head 1 regresses **P(win)** (the discounted ±1 outcome). The search combines them at a leaf as `V_shaped·VALUE_SCALE + TWOHEAD_WIN_WEIGHT·P(win)` and adds the same `±TWOHEAD_WIN_WEIGHT` (300) to a terminal edge, so a win still outranks the best near-win (the winloss/blend goal) — but the ranking pressure lives in the *bounded* P(win) head and never poisons the shaped estimate (blend's failure). `value_mode="twohead"` builds a 2-output value head, baked into the checkpoint like `hidden`, so it needs a **fresh run** and cannot `--resume` a single-head checkpoint (`load_policy` defaults `value_dim=1` for old checkpoints — `az.pt` still loads). Cold 64-net run + a `--resume` (iter 100→200) to `src/ai/az_twohead.pt`. **Tried, failed (2026-07-13): 0/6** at equal budget (both gate and final ckpt; `baselines --az src/ai/az_twohead.pt --az-sims 300 --az-value-mode twohead --mcts-sims 300 --seeds 6`). It clears *more* than blend (113-138) and survives longer, and its self-play won sporadically (12.5%), but it never finishes on the benchmark seeds — the same "farm, don't finish" wall. So the clean value-side ranking fix does not beat 3/6 either.

**The reward-side ranking lever: `az_train --reward-win V` (2026-07-13, prepared).** `blend`/`twohead` inject the win/near-win ranking on the *search/value* side while leaving `REWARD_WIN` at +100. The complementary lever changes the reward itself: raise `REWARD_WIN` (e.g. 800) so a win's *discounted* return-to-go clears the near-win band directly. Why it is well-founded and *distinct from blend*: to win you clear all 36 flames (+360) **and** take `REWARD_WIN`, so a win already beats a near-win in *raw* return — the failure is **discounting**, the +100 terminal seen from a ~60-ply-early state is only ~+55 and is swamped by clear-count noise; ×8 makes it ~+440, a signal the value target can separate. It is **asymmetric** (`REWARD_DEATH` untouched), so unlike blend's ±300 spike it never poisons the value near a death. **Do not also raise `REWARD_CLEAR_FLAME`** — clear (+360) is *already* the term that swamps the win, so raising it widens the very near-win band this fights (a common wrong instinct). Implemented as an `az_train --reward-win` / `baselines --reward-win` override of `constant.REWARD_WIN` (read dynamically in `game.step`, so it reaches self-play, the MCTS bootstrap and eval alike); a distinct reward scale = a **full retrain**, so use a distinct `--out/--checkpoint` (never `az.pt`) and benchmark with the *same* `--reward-win`. **Pair it with `--value-scale`** (override of `alphazero.VALUE_SCALE`, default 100): the value target is divided by `VALUE_SCALE` to keep the value loss O(1), so a larger `REWARD_WIN` needs a *proportional* `VALUE_SCALE` (use `--reward-win 800 --value-scale 800`, on train *and* `baselines`) — omitting it makes the win target ~8, the value MSE ~O(10), and the value gradient re-crushes the policy head through the shared trunk (measured: `v_loss` 3.6→9.8 climbing, `p_loss` *rising* 2.13→2.26 — the exact pre-VALUE_SCALE-fix pathology). It is pure normalisation and does **not** touch the win/clear ranking (that lives in the raw reward). Keep V ≲ ~1000: `best_score`'s win-rate band is `win_rate*100_000` (≈+6250 per win-in-16), which must stay above the whole `mean_reward` range — a full clear + win at V=800 is ~1160, safely under. **Tried, failed (2026-07-14): `--reward-win 800 --value-scale 800`, cold 64-net, 100 iters.** In *training* it was the strongest signal of the whole project — `clear` climbed to +241 (~24 flames), `stall` stayed low (−14), `terminal` went *positive* on the full game for the first time (+136/+35/+88), and `eval_win@120` peaked at 18.8%. But at equal budget it is **0/6** (and **0/12** on the extended check): the final net clears 262 and survives 53.5 plies — the closest any learned net has come to MCTS (310/57) — yet **never finishes** on the benchmark seeds. (Note: raising REWARD_WIN also *hurt* MCTS itself, 3/6→2/6, exactly the "too-high win washes out the dense guidance → toward winloss" effect — so 800 may even be past the sweet spot.) The verdict confirms the prediction: the wall is win *discovery/finishing*, not the value/reward scale.

**The four ranking/reward levers are exhausted — the wall is win discovery, so attack the buffer (2026-07-14, running).** `winloss` (0%, collapse), `blend` (0/6), `twohead` (0/6), `--reward-win 800` (0/6, 0/12) all fail: every value/reward variant produces a net that *plays* well (clears ~24-26 flames, survives near-MCTS) but *finishes* nothing. The common cause is upstream of the value target: the replay buffer is a rolling `deque(maxlen=20000)`, wins are ~0.3% of samples and evict within ~40 iters, so the rare wins (self-play *and* the MCTS bootstrap's) are washed out before the net can imitate them — "more iterations don't help while no win reaches the buffer", now understood as "…*stays* in the buffer". The **buffer lever** (`az_train --win-buffer-frac F`, default 0 = off, byte-for-byte unchanged) adds a **persistent win-only buffer** (`deque(maxlen=40000)`, never evicted by non-wins), fed by every winning self-play and bootstrap game, from which fraction `F` of *every* SGD minibatch is drawn (with replacement) — so winning trajectories are permanently represented no matter how rare. It attacks the actual wall rather than the scale. Recipe: `--curriculum --value-target shaped --win-buffer-frac 0.25 --simulations 300 --bootstrap-games 8 --iterations 100 --out src/ai/az_wbuf.pt` — the bootstrap seeds the win buffer with MCTS wins, and `--win-buffer-frac` keeps them there. Risk to watch: with only ~4-8 bootstrap wins on stage 8, 25% of every batch imitates a *few* MCTS lines → possible **overfit to those seeds** that does not transfer to the benchmark's flame patterns (watch a high train `selfplay_win`/low `eval_win` split; the fix is more `--bootstrap-games` for line diversity). Verdict = the usual `baselines --az src/ai/az_wbuf.pt --az-sims 300 --mcts-sims 300 --seeds 6` vs 3/6.

**Buffer lever — the first learned agent to improve past 1/6, but plateaus at 2/6 (2026-07-15).** The one lever that *moves*, and the only one to reach MCTS's flame-clearing. Trajectory over three 100-iter sessions (`--win-buffer-frac 0.25 --simulations 300 --bootstrap-games 8`, one `shaped`-target 64-net, chained `--resume`s to `src/ai/az_wbuf.pt`): **1/6 → 2/6 → 2/6**. First session (through the ramp to the full game) benched **1/6** (clear 205, survive 51 plies) — already better than the 0/6 of every ranking/reward lever, and the *first 64-net whose self-play wins the full game at all* (`selfplay_win` 12-37% recurring, vs the chronic 0% — the buffer lever did what it was designed to: put and keep wins in the buffer). A `--resume` (iter 130→230) lifted it to **2/6** (clear **320 > MCTS's 318**, survives **66.8 > MCTS's 56** plies, terminal +26.7) with a project-record `eval_win@120` spike of 31.2% at iter 200 — the saved gate pick. A second `--resume` with reinforced `--bootstrap-games 16` (iter 230→330) **did not improve**: both gate pick and final ckpt stayed **2/6**, and the final ckpt's stats even dipped slightly (clear 301, survive 57), `eval_win@120` capped at 12.5% all session with `p_loss` still falling 1.95→1.73 — the "more iterations don't help" wall, now at 2/6. So the buffer lever's honest ceiling is **2/6: below MCTS/`az.pt`'s 3/6, above every other lever's 0/6**. It clears as many flames as MCTS and survives longer, but finishes one seed short. (Snapshots in `tmp/`: `az_wbuf_gate_iter200_2of6.pt`, `az_wbuf_final_iter330_2of6.pt`.) **One clean thing remains untried: the win-buffer *carry*.** The persistent buffer was persistent only *within* a session — it lives in RAM, not the checkpoint, so each `--resume` re-warmed from an empty buffer (~30 iters). Commit `fdf1f8b` fixes that: a `<checkpoint>.winbuf` sidecar saves the win buffer at each checkpoint and reloads it on `--resume` (samples store only `(obs, mask, visit-π, return-to-go)`, none net-dependent, so a carried win stays valid — targets don't go stale, only the state distribution is off-policy; `--win-buffer-frac 0` writes/reads no sidecar, unchanged). The iter-330 checkpoint now *has* a sidecar (4.1 MB), so the next `--resume` will **carry** ~5k win samples from iter 1 instead of rebuilding — the actual test of the lever's premise.

**Buffer carry tested — mechanism works, ceiling does not move: still 2/6 (2026-07-15).** A fourth `--resume` (iter 330→430, same recipe, `--bootstrap-games 16`) with the sidecar in place started **warm** for the first time — logged `Restored win buffer: 5729 samples`, and the win buffer grew 5729→16379 across the session instead of the ~358 a cold start rebuilds by this point. So the carry does exactly what it claims mechanically. It also produced the *strongest training dynamics* of any buffer session — `selfplay_win` peaked at 50% (vs 12-37% cold), `eval_win@120` touched 25% twice (vs the 12.5% cap of the cold `--resume`), and `p_loss` set a new floor of 1.646 (vs 1.73). **But none of that crossed the benchmark ceiling.** No eval@120 beat the saved 31.2% gate, so `az_wbuf.pt` was never rewritten (still the iter-200 gate pick). The final iter-430 net, extracted and benchmarked at equal budget (`baselines --az tmp/az_wbuf_final_iter430.pt --az-sims 300 --mcts-sims 300 --seeds 6`), scored **2/6 (33.3%, return 265, clear 252, terminal +24, survives 53 plies)** — the same 2/6 plateau as the cold resumes, below MCTS's 3/6. **Verdict: the buffer *carry* improves training signal (stronger self-play, lower p_loss) but not the win rate — the buffer lever is confirmed capped at 2/6, and win *persistence across sessions* was not the binding constraint.** This closes the buffer lever: cold and carried resumes both plateau at 2/6. Every lever tried (ranking, reward, buffer, buffer-carry) leaves the ceiling where MCTS's ~50% teacher sets it; breaking past 3/6 needs a *stronger-than-MCTS* bootstrap source or a different leaf-value signal, not more/better-retained wins from the same ~50% teacher. (Snapshot: `tmp/az_wbuf_final_iter430.pt` = the 2/6 carry net; `tmp/az_wbuf_ckpt_iter430.pt(.winbuf)` = its checkpoint + carried buffer.)

**Multi-seed MCTS teacher — lifts the learned agent from 2/6 to 3/6, matching MCTS at equal budget (2026-07-16).** The diagnosis "the teacher is only ~50%, so the student caps there" has a subtlety the buffer lever missed: single-seed MCTS wins ~50%, but *which* seeds it wins is set by the rollout RNG — no seed is unwinnable, a different RNG wins a different one (the aggregate-30-games finding: every eval seed is won by *some* run). So a plain bootstrap only ever seeds the buffer with the ~half of games MCTS *happened* to win, and the net learns those patterns and not the rest — plausibly the real reason the buffer lever stalled at 2/6, i.e. a **coverage** gap, not a teacher-strength gap. The `--bootstrap-win-retries R` lever (commit `f1480b2`) attacks exactly that: each bootstrap slot re-rolls fresh game seeds until MCTS *wins* (cap `1+R` attempts), keeping only the winning line, so the win buffer covers the pattern space instead of the lucky half. `retries=0` is byte-for-byte the old single-attempt path. At stage 8 the retries visibly engage — a slot needs ~3 games/win (measured "24 games" and "28 games" for 8 slots, ~33% first-try full-game win rate), yielding **7/8 diverse full-game winning lines** per bootstrap vs ~4 single-seed. Recipe: a cold 64-net at the proven buffer recipe **plus** `--bootstrap-win-retries 4` (`--curriculum --value-target shaped --win-buffer-frac 0.25 --simulations 300 --bootstrap-games 8 --bootstrap-win-retries 4 --iterations 100 --out src/ai/az_mseed.pt`), then one `--resume` (iter 100→200; the cold run reached stage 8 only at iter ~77 so its policy head was far from mature, `p_loss` 2.26). The resumed iter-200 net — **still undertrained** (`p_loss` 1.96 vs a mature net's ~1.65) — benched **3/6 (50%, return 355, clear 305, terminal +43, survives 58.3 plies) at equal 300-sim budget, a dead heat with MCTS** (`baselines --az tmp/az_mseed_iter200_3of6.pt --az-sims 300 --mcts-sims 300 --seeds 6`: MCTS 374/318/45/56.0). It *finishes* (terminal +43, near MCTS's +45) and survives *longer* than MCTS (58.3 > 56 plies). This is the first lever to move the learned ceiling past the plain buffer's 2/6 — the win-line *diversity* was a real binding constraint, distinct from teacher strength. Two honest caveats: (1) 3/6 **matches** MCTS/`az.pt`, it does not yet **exceed** the ~50% ceiling — the teacher is still MCTS, so this confirms "reach the teacher," not "beat it"; (2) the net was still improving at the cut (`p_loss` falling, `eval_win@120` peaked at 18.75% not yet plateaued), so a further `--resume` is the obvious next probe — it could either firm up 3/6 or, if diversity keeps helping, be the first to reach 4/6. Snapshots in `tmp/`: `az_mseed_iter200_3of6.pt` (the net), `az_mseed_ckpt_iter200_3of6.pt(.winbuf)` (checkpoint + carried win buffer, ready to resume). A companion fix (commit `2f3b87e`) **skips the startup bootstrap on a carry-resume** (the restored win buffer already holds those lines; re-running the multi-seed bootstrap at stage 8 costs ~1h to recompute them) — promotion bootstraps still run; cold/non-carry runs unchanged.

**The multi-seed resume settles it: 3/6 is the ceiling, and beware the gate's selection effect (2026-07-16).** Caveat (2) above was tested — a second `--resume` (iter 200→300, same recipe, carried buffer, so the startup bootstrap was correctly skipped). The net *did* keep learning, exactly as predicted: `p_loss` 1.963 → **1.715**, `selfplay_win` peaked at **50%**, and `eval_win@120` hit **50%** at iter 240 (a project record, vs the prior 31.2%). **None of it raised the win rate.** Three measurements agree the net is at MCTS's level, not past it:
- **final iter-300 net** (no selection): **3/6** at equal budget (return 360, clear 307, terminal +44) — dead-on MCTS's 3/6 (374/318/45) despite the lowest `p_loss` of any run.
- **gate pick iter-240** on the usual `EVAL_SEEDS[:6]`: **5/6 (83.3%!)**, beating MCTS on every column (clear 337, terminal +82) — which is an **artefact**, see below.
- **gate pick iter-240 on held-out seeds**: **3/8 (37.5%)** vs MCTS's **4/8** — i.e. the *same net* drops from 83% to 37.5% once the seeds are ones the gate never saw. (One game's difference from MCTS on 8 seeds = a dead heat, not "below".)

**The methodological trap, which nearly got recorded as "first agent to beat MCTS".** The training gate evaluates on `EVAL_SEEDS[:16]` (`AZConfig.eval_seeds`), and the standard benchmark uses `EVAL_SEEDS[:6]` — **a subset**. So the saved "best" snapshot is chosen partly *on the very seeds it is then scored on*. At 120 sims the gate metric is so noisy (it oscillated 0% → 50% → 6% between consecutive evals of one run) that over ~20 evals it reliably picks a **lucky** snapshot, and the benchmark then re-measures that same luck. The inflation is huge — 83.3% biased vs 37.5% unbiased for one net. **Rule: never report a `--seeds 6` benchmark of a gate-selected snapshot as evidence of a real gain.** Verify on seeds the gate never saw — `baselines --seed-offset 16` starts the seed window past the gate's range: `baselines --az <net.pt> --az-sims 300 --mcts-sims 300 --seeds 8 --seed-offset 16`. (This also means every "N/6" in this file for a gate-picked net is an *upper* bound; the unselected iter-300 net's 3/6 and MCTS's own 3/6-4/8 — MCTS is never gate-selected — are the trustworthy figures. Judging AZ by `eval_win@120` remains wrong for the *opposite* reason too: it understates a net's 300-sim strength. Both errors argue for the same fix — evaluate at the budget you benchmark at, on seeds you did not select on.)

**Verdict: the multi-seed lever reaches the teacher and stops there, like every lever before it.** 2/6 → 3/6 was real (win-line diversity was a genuine constraint), but 3/6 = MCTS's rate is where it plateaus, now confirmed with a *converged* net (`p_loss` 1.715, flat) rather than an undertrained one — so "it was still improving" is retired as an explanation. Six independent levers (ranking, reward, buffer, buffer-carry, multi-seed, and more iterations at two widths) all land on ~50%: **the ceiling is the MCTS teacher itself**, and no amount of better-retained, better-covered, better-imitated MCTS data crosses it. Breaking 3/6 requires a teacher *stronger* than MCTS. The cheap diagnostic to pick the next lever (~1h, no retrain): benchmark `az.pt` at 600 and 1000 sims vs MCTS at 300. MCTS provably does *not* scale with budget (300→600 sims and `rollout_depth` 16→64 change nothing — its `safe_greedy` leaf is noise), whereas AZ's leaf is a *learned* value that should sharpen with a deeper tree. If AZ's win rate rises with sims, the **flywheel** is viable (bootstrap the next generation from AZ@1000 rather than MCTS@300 — a >50% teacher, and self-improving); if it too flatlines, the search class itself is exhausted and the remaining option is a different algorithm (a deterministic best-first/proof-number solver toward the win predicate). Snapshots: `tmp/az_mseed_final_iter300_3of6.pt` (converged net, honest 3/6), `tmp/az_mseed_gate_iter240_3of8heldout.pt` (the "83%" net, 3/8 held-out — kept as the selection-effect exhibit), `tmp/az_mseed_ckpt_iter300.pt(.winbuf)`.

**AZ's *play* scales with budget where MCTS's does not — but its *wins* do not, so the flywheel's premise fails (2026-07-16).** The diagnostic the box above prescribes, run on **held-out** seeds (`baselines --az src/ai/az.pt --az-sims {300,600,1000} --seeds 8 --seed-offset 16`; `az.pt` is itself gate-picked, so its usual "3/6" is not a valid baseline to measure a trend from):

| az.pt @ sims | win% | return | clear | survive | terminal |
|---|---|---|---|---|---|
| 300 | 62.5 (5/8) | 386.85 | 317.50 | 57.75 | +58.75 |
| 600 | 62.5 (5/8) | 404.40 | 333.75 | 58.88 | +58.75 |
| 1000 | **75.0 (6/8)** | 431.54 | 350.00 | 61.25 | +72.50 |
| *mcts @300 (anchor, same seeds)* | *50.0 (4/8)* | *373.48* | *317.50* | *55.50* | *+44.38* |

**Read the secondary columns, not the win rate**: 5/8 → 6/8 is *one game* and proves nothing on its own (see the selection-effect box — differences of 1-2 games at this sample size are indistinguishable from noise). The signal is that `return` (387→404→432), `clear` (317→334→350), `survive` (57.8→58.9→61.3) and `terminal` (+58.8→+58.8→+72.5) rise **monotonically and without exception** at every budget step — four metrics, each aggregating far more events than the binary win counter, all agreeing. This is the first **qualitative asymmetry** measured between the two searches: MCTS is *known* not to scale (300→600 sims and `rollout_depth` 16→64 both change nothing — its `safe_greedy` leaf is noise, so more search only refines a biased estimate), whereas AZ's *learned* value converts budget into play at every step, exactly as the leaf-quality theory predicts. **The replication (same net, 300 vs 1000, on a second, non-overlapping held-out set `EVAL_SEEDS[24:32]`) splits the result cleanly:**

| | Δ win | Δ clear | Δ return | Δ survive |
|---|---|---|---|---|
| run 1 (seeds 16:24) | **+1 game** | +32.50 | +44.69 | +3.50 |
| run 2 (seeds 24:32) | **+0 game** | +47.50 | +45.54 | +4.87 |

**The play-quality scaling replicates; the win scaling does not.** `clear`/`return`/`survive` rise by near-identical amounts in both independent samples — that effect is real and is a genuine asymmetry vs MCTS (which is flat in budget). But the win rate went +1 then +0: combined over all **16** held-out seeds, tripling the budget buys **one win in sixteen** (9/16 → 10/16, 56.2% → 62.5%), i.e. nothing measurable. The 5/8→6/8 of run 1 was the noise it looked like.

**The decisive fact, and the one that should drive what comes next: at 1000 sims the agent clears 34.8 of 36 flames on average and still loses half its games.** The wall is not finding flames, not surviving long (61 plies), and not search depth — it is **finishing**. (**Correction, 2026-07-16**: an earlier version of this box inferred "it dies with one or two flames left" from that 34.8 mean. That inference is **wrong** — the mean is dominated by the *wins*, which clear all 36. Direct measurement over the actual losses puts it at **9.7 flames left at death**; see the autopsy box below.) This is the same "farms, doesn't finish" signature as every value/reward lever, now reproduced on the search-budget axis that was supposed to be the way out.

**So the flywheel loses its premise.** What a teacher supplies is *winning lines* for the buffer, and on that AZ@1000 (10/16 = 62.5%) does not measurably exceed MCTS@300 (4/8 = 50% on the same seeds) — one game of difference. Bootstrapping a generation from a 62%-teacher instead of a 50%-one, on that evidence, would very likely replay the previous six levers. **Recommended instead: stop hunting a stronger teacher and instrument the losses.** No one has yet looked at a single defeat — replay the lost games and inspect the state at death (flames left, PA, geometry, which wave). An agent that clears 96% of the board and loses half the time has a *structural* endgame problem that a generic teacher will not fix, and six levers were spent optimising means without ever examining a loss. (Footnote: `az.pt` scores *higher* on held-out seeds (5/8) than on its own selection seeds (3/6) — the opposite of selection inflation, i.e. plain noise; another reminder that every "N/6" in this file is ±1-2 games.)

**Autopsy of the losses — the deaths are zugzwangs at ~10 flames, and the search is NOT broken (2026-07-16).** Six levers optimised means; nobody had replayed a single defeat. `tmp/autopsy.py` does (`--net src/ai/az.pt --sims 300 --seeds 8 --seed-offset 16`): it replays games, classifies each death, and probes whether any legal action survived one ply. On held-out seeds, `az.pt` @300 went 5 wins / 3 losses, and every loss looks the same:

| seed | cause | plies | flames left | survivable actions | fatal action |
|---|---|---|---|---|---|
| 1623 | instant | 51 | 9 | 1/16 | ShortJump(0,1) |
| 1724 | instant | 51 | 10 | 11/17 | ShortJump(1,0) |
| 2330 | instant | 49 | 10 | 11/17 | ShortJump(-1,0) |

Three facts, each killing a plausible story. **(1) No attrition.** Every death is a flame reaching the player (`hp` drops from N>1 straight to 0), never the endgame HP drain (`end_turn` costs 1 hp once all waves have spawned — game.py:302 — which turns out to be a non-issue at 40 HP). **(2) It dies with ~9.7 flames left**, not 1-2 — a third of the board, ~10 plies before a winning line would end. **(3) The fatal positions are zugzwangs, not blunders.** At the seed-1724 death, all 11 "surviving" actions have `approach ≤ 0` (retreat, `MoveFlames`, or end-turn) and *every* action with `approach +1` — i.e. every move that makes progress toward a flame — dies. Clearing requires approaching; approaching kills. **The wall is that positions exist from which no progress is survivable, and the agent reaches them with a third of the board still burning.**

**A measured-but-refuted search pathology (kept so nobody re-runs it).** The autopsy exposed something that looks damning: `_search` shares ONE `_MinMaxStats` over the whole tree and it only ever *widens*, so a first-visit leaf estimate (~+146, later revised to ~+7 by deeper search) permanently inflates `hi`. Measured at the seed-1724 fatal state: global range `[-10.18, +146.45]` vs a root Q spread of only `[-10.18, +11.92]` — the root's live-or-die contrast normalises to **14% of [0,1]**, PUCT scores all equilibrate to ~0.155, and visits track the **prior**, not Q (the fatal action had prior 0.447 / Q -9.18 / **77 visits**; the best action had prior 0.019 / Q +11.92 / 12 visits). Since the played move is the most-visited one, this reads as "the search is decorative — it replays the policy head". **Two fixes were tried and both are much worse than the shipped search:**

| root rule | win% | return | clear | terminal |
|---|---|---|---|---|
| **shipped (global min-max + most-visited)** | **62.5 (5/8)** | **386.85** | **317.50** | **+58.75** |
| argmax Q (min 5 visits) — `tmp/bench_qpick.py` | 12.5 (1/8) | 233.58 | 251.25 | +2.50 |
| per-node min-max — `tmp/bench_pernode.py` | 0.0 (0/8) | 206.86 | 233.75 | -11.25 |

So the *facts* hold but the *conclusion* does not. Visit counts are the robust statistic — they aggregate the whole subtree, whereas a lightly-visited action's Q is biased noise; that is exactly why the literature selects on visits, and these numbers re-derive it the hard way. Per-node normalisation is worse still: with few visited children `lo`/`hi` collapse onto two samples, so noise-level Q gaps stretch to full [0,1] contrast and the search over-commits to whatever it saw first. The global scale is doing real work. The seed-1724 "77 visits on the worst Q" is a **real but rare** pathology; promoting it to a rule costs 4 wins in 8. **Do not re-litigate the search's selection rule without evidence stronger than one dissected state.**

**Walking the losses back: the fatal move is a *symptom*, and the game is not lost at any locatable moment (2026-07-16).** `tmp/trap.py` traces every ply of won and lost games, counting `safe` / `clear` / `clear_safe` actions plus flame clustering. It kills the natural follow-up story ("find the move that creates the zugzwang"):
- **The zugzwang is transient and routine, not a trap that closes.** In lost seed 1724, `clear_safe == 0` occurs at plies **10, 13, 42, 45, 46 and 50**. The agent handles it correctly five times (retreat/stall/`MoveFlames`, and progress reopens next ply) and dies on the sixth. Across all 8 held-out seeds, losses keep a safe clearing move until **1 ply before death** — so no version of "it was doomed 20 plies ago and wandering" survives.
- **Removing the fatal move changes nothing.** A root 1-ply survival filter (`tmp/bench_safe.py` — never play a root action that dies when another survives; the selection rule untouched) *does* fix all three measured fatal moves, and scores **5/8 — identical to the shipped 5/8**, with `terminal` identical to the cent (+58.75), i.e. **the same games won and lost**. It survives 2 plies longer (59.6 vs 57.8) and clears slightly more (320 vs 317.5), then loses the same seeds. The agent does not lose *because* it plays the fatal move; it plays the fatal move *because* it has already lost (its own Q agrees — at the fatal state every option is ≈ -9).

**Why averaging fails, and it sharpens the picture.** The premise was that inter-tree disagreement is *noise around a best move* that averaging would clean up. It is not. A pre-check is stark: four trees differing only in rollout RNG propose **three different moves** in the same position at 300 sims each — a single search does not converge on a best move, it *samples* a plausible one. The disagreement is real: each tree has committed to a **different winning line**, and winning demands following **one** precise ~60-move line. Averaging four trees committed to four lines yields a consensus move belonging to **none** of them — it does not reduce noise, it destroys commitment. (Same shape as the two search "fixes" that failed earlier: both smoothed a decision that must stay sharp.) So four configs now sit at 50-75%, each on a different subset, union 100%: **nothing crosses the band; everything moves it.** *Footnote:* the flame total is **not** a fixed 36 — wins show `clear` of 340-360, so patterns differ in flame count and per-seed "N/36" figures elsewhere in this file are approximate.

**So five independent stories about the losses are now refuted** (each measured, none surviving): endgame HP attrition (no death is attrition); "dies with 1-2 flames left" (it is 9.7); a broken search (both fixes far worse — see the box above); HP waste (wins waste more); and a locatable fatal blunder (filtering it changes no outcome). **The agent is not making a repairable mistake** in any single ply — and the winnability box above says why that search was doomed: the losses have no deterministic local cause to find. (One claim there is now *withdrawn*: the seed-1724 fatal position was called "already lost". It is not — az@1000 wins that very seed. The position was mis-evaluated, not lost, which is why the survival filter could not rescue it: dodging the death is not the same as finding the line.)

**`best_score` is lexicographic** (`stage_idx * 10_000_000 + win_rate * 100_000 + mean_reward`). It used to be `stage*1e6 + win_rate*1000 + mean_reward`, where one win in 16 was worth only +62.5 — less than the spread in shaped reward — so **a 0%-win policy overwrote the 6.2% full-game winner in `az.pt`**. The win-rate band must stay wider than the shaped reward's whole range (which reaches ~500 on a win). Checkpoints written before this fix carry an old-scale `best_score` and must not be `--resume`d.

**Curriculum knobs on `Game.__init__`** (`num_waves`, `flames_per_wave`, `spawn_radius`, `spawn_formation`, all `None` = full difficulty): shrink the game to a winnable size so PPO has a reward gradient. `spawn_radius` (when set) replaces the fixed spawn *patterns* with `flames_per_wave` flames placed on random free tiles within that Manhattan distance of the player — the real difficulty is spawn *distance*, so a small radius + 1 flame is a trivial win. `spawn_formation="line"` overrides both and spawns a *fixed shape*: `flames_per_wave` mutually adjacent flames in a straight line on the player's own row or column, starting `constant.SPAWN_LINE_OFFSET` (=2, LongJump reach) tiles away, direction drawn from the 4 orthogonals, falling back to `_near_spawn` near a map edge. `reset()` preserves all four; `_make_wave()` applies them at spawn time, formation winning over radius winning over the drawn pattern.

**Why the `line` stage exists.** The radius stages never put two flames *adjacent to each other*, so nothing in the ramp teaches the push-chain death (land on a flame → `push_flames` shoves its neighbour into the next one → instant death), and the full game opens with six flames. `line` is that missing bridge, and it is calibrated: measured over 6 seeds, `random` **0/6**, `greedy_clear` **0/6** (its first jump kills it — the very reflex the earlier stages reward), `mcts` at 300 sims **6/6**. Hard, winnable, and lethal to the greedy heuristic. If you add another formation, verify it the same way before training on it: **a stage nobody can win stalls the curriculum at 0% forever**, since promotion is the only way forward and there is no demotion.

**Environment API on `Game`** (all in `src/game.py`):
- `get_observation() -> list[float]` — fixed-length egocentric vector. Layout: 11 scalars `[px, py, hp, pa, waves, flame_count, boss_dx, boss_dy, castable_0..2]`, then the `K_NEAREST_FLAMES` nearest flames and `K_NEAREST_SPAWN` nearest next-spawn tiles, each `(present, dx, dy)`, all normalised to ~`[-1, 1]`. Length is `observation_size()` (currently **53**). `K_NEAREST_FLAMES`/`K_NEAREST_SPAWN` live in `constant.py`.
- `clone() -> Game` / `get_state() -> dict` / `set_state(dict)` — **state save/restore for search agents** (the game is deterministic, so a clone/snapshot can be stepped freely without touching the original). `clone()` is a `deepcopy` (~4 ms). Spell sprites are lazy, and `Spells.__deepcopy__` drops the cached `_image` (a `pygame.Surface` can't be deep-copied), so `clone()` stays safe **even after the game has been rendered** — this matters for `play.py --sims` (watching the search agent live), where drawing the spells loads the surfaces before the per-move clone. `get_state`/`set_state` are a ~80x-cheaper fast path (~80/140 µs) capturing only the mutable fields (player pos/hp/pa, flame occupancy, per-turn spell `time_used`, wave/turn/done/won counters, both RNGs, `spawn_pattern`/`previsu`/`spell`/`last_reward`) — the map structure and never-moving Bolgrot are shared. `set_state` rebuilds flame + player occupancy while keeping the *same* `player` object (it is aliased from `Game.player` and its cell). Used by `mcts.py` and `alphazero.py`; verified behaviourally identical to `clone`.
- `ACTIONS` (module-level `_ACTIONS`, aliased as `Game.ACTIONS`) — the fixed discrete action space, **17** entries. Each is `(spell_index | None, (dx, dy))`; the target tile is the player's position plus the offset. Because every spell targets one of 4 orthogonal / 4 diagonal directions at range 1–2, the space collapses to ShortJump×4 + LongJump×8 (range 1 and 2) + MoveFlames×4 + one end-turn (`(None, (0, 0))`, the last index). This makes the target position-independent so the policy never has to output an arbitrary tile.
- `legal_actions() -> list[bool]` — mask over `ACTIONS`. End-turn is always legal while live; a spell action is legal only when the spell `is_castable` **and** its target tile is in the spell's `previsu()`. All-illegal once `done`.
**HP is the game's currency, not a health bar (2026-07-16 — this was missing from these notes and it reframes the economy).** Every action is paid for in HP: `ShortJump`/`LongJump` cost **-1 HP** (`short_jump.py:75`, `long_jump.py:74`) and refund **+1** when they land on a flame (`:72`/`:71`) — so *a clearing jump is free and a whiff costs 1* — while `MoveFlames` costs a flat **-5 HP** (`move_flames.py:55`). `MAX_HP` is 40, so a game affords roughly **40 unproductive actions in total**, and every measured trace ends between 1 and 11 HP whether won or lost: the economy is tight start to finish. Separately, once every wave has spawned each `end_turn` drains **1 HP** (`game.py:302`) — a shot clock, but at 40 HP it never binds (no measured death is attrition). **The shaping badly under-prices all this**: `REWARD_HP_DELTA` is `0.02`/HP, so the whole 40-HP bar is worth **0.8** — under a tenth of one flame (+10), and a wasted `MoveFlames` costs 0.3 of reward for 12.5% of the game's budget. (Tempting but **refuted**: opening HP waste does *not* predict losses — over 8 held-out seeds the *wins* burned more on an empty board than the losses, 11.4 vs 10.7 mean. Do not "fix" this expecting wins.)

**Two moves of margin, all game long.** `tmp/trap.py` probes every ply for how many of the ~17 legal actions **clear a flame and survive** (`clear_safe`). On `az.pt` @300 it is **never above 4 and usually 2**. That is the real shape of the game: at any moment about two of seventeen moves make safe progress, and a win needs ~36 of them chained without a miss, on a ~40-action error budget. This explains the ~50-60% ceiling better than any teacher/value/buffer story — the margin is structural.

- `step(action_index) -> (reward, done)` — applies one action (all weights are `REWARD_*` constants in `constant.py`). A flame is removed **only by jumping onto its tile** (`ShortJump`/`LongJump` `play()` overwrite `dst.entity` and refund +1 HP); `attract_flames` merely repositions flames, so "kill all flames" means landing on each one before the waves overwhelm you. Reward terms: `REWARD_CLEAR_FLAME` (`10.0`) per flame removed — the dominant progress signal; `REWARD_SURVIVE_TURN` (`0.1`) token per end-turn; `REWARD_END_TURN_PER_FLAME` (`-0.5`) × flames still **alive on the board** at end-turn (the `"stall"` part, measured *before* the wave spawns so only flames the agent left uncleared count — this is the controllable anti-stall term: a clean board nets +`REWARD_SURVIVE_TURN`, an uncleared board goes net-negative; magnitude kept well under the death penalty so suicide never becomes preferable); `REWARD_HP_DELTA` (`0.02 × ΔHP`); terminal `REWARD_WIN` (`+100`); terminal death `REWARD_DEATH` (`-10`) **plus** `REWARD_DEATH_PER_WAVE_LEFT` (`-5.0`) × waves still unspawned, so dying early is far worse than dying on the brink (this is what makes surviving beat "clear a few then die"); `REWARD_ILLEGAL` for masked-out no-ops. **Only flame *reductions* pay** (`if cleared > 0`) — the end-turn wave adds flames the agent can't prevent. Two shaping terms: `REWARD_APPROACH` (`1.0` per tile closer to the nearest flame/next-spawn tile, measured old-vs-new player position against a fixed snapshot, so only the two jumps earn it), and a per-spell cast bias `REWARD_CAST` (now `(0.0, 0.0, -0.2)` — kept near zero because an *unconditional* per-cast reward is farmable; only the no-progress "Inaction" drag keeps a small negative). `step` also stores a per-term breakdown dict in `self.last_reward` (keys = `REWARD_PARTS`, sums to the returned scalar) so tooling can see *which* term a policy accumulates. Episodes always terminate because HP/PA are finite. **Changing any `REWARD_*` requires retraining** but *not* a dimension change, since the observation and action space are unchanged.

**`src/ai/` modules** (nothing here contains game logic; keep `__init__.py` import-free so the base game never needs `torch`):
- `network.py` — `ActorCritic`, a small shared-trunk MLP (`obs_size → 64 → 64 → {policy logits, value}`, orthogonal init). Illegal-action masking is centralised here: `get_action_and_value(obs, mask, action=None)` fills masked logits with `MASK_FILL` (`-1e8`) before the `Categorical`, so the policy can only pick legal moves. Rebuild dims from `Game.observation_size()` / `Game.num_actions()`.
- `policy.py` — env↔net glue: `choose_action(net, game, deterministic)` (greedy argmax over masked logits, or sampled), `run_episode`/`evaluate` (mean reward + win rate over the fixed `EVAL_SEEDS`), and `save_policy`/`load_policy` (a checkpoint stores the state dict plus `obs_size`/`num_actions`/`hidden` so it rebuilds standalone). `MAX_STEPS` is a safety cap. Reward-decomposition helpers live here too: the `ActionFn` type (`Game -> action index`) and `net_action_fn(net)` let scripted and neural policies share `run_episode_decomposed` (returns `(total, won, steps, parts)`); `evaluate_decomposed` averages those `parts` over `EVAL_SEEDS`, and `format_reward_parts` renders the compact `name +value` line the trainer logs each eval.
- `baselines.py` — offline reward-balance harness. `python -m src.ai.baselines [--policy src/ai/ppo.pt] [--mcts-sims N] [--az PATH] [--az-sims N] [--seeds N]` scores scripted policies (`always_end_turn`, `random_legal`, `greedy_clear`) plus the trained net over `EVAL_SEEDS` and prints a **policy × reward-term** table (via `score_policy`/`benchmark`). `--mcts-sims N` adds an MCTS row at that per-move sim budget; `--az PATH` adds an AlphaZero (net-guided PUCT) row at `--az-sims` sims/move (both slow — pair with `--seeds N` to shrink the seed set). `--seeds N [--seed-offset K]` scores `EVAL_SEEDS[K:K+N]`; **use `--seed-offset 16` whenever the net came from a training gate** — the gate selects on `EVAL_SEEDS[:16]`, so the default window scores a net on its own selection seeds (see the selection-effect box below). Balancing `REWARD_*` is an *ordering* problem: read down the `return` column (a winning policy must beat clearing-then-dying must beat sitting still) and across a row (whichever term dominates a non-winning policy is the one being over-paid). No game logic — pure env-driven tooling.
- `ppo.py` — the algorithm. `PPOConfig` holds hyperparameters (CleanRL-style defaults). `_VecGames` steps `num_envs` independent games in lockstep with auto-reset. `_compute_gae` does GAE over the `[num_steps, num_envs]` rollout; `train(cfg)` runs rollout → GAE → clipped-surrogate + value + entropy update, and saves the best-by-eval policy to `cfg.out_path`. **The env is not a `gym` env** — it's driven directly through `get_observation`/`legal_actions`/`step`, and the legal-action mask is stored per step so the PPO update re-masks identically.
- `train.py` — `python -m src.ai.train [--iterations N] [--num-envs N] [--num-steps N] [--lr] [--lr-floor F] [--ent-coef E] [--seed] [--out ppo.pt] [--checkpoint ppo_ckpt.pt] [--resume [PATH]] [--curriculum] [--promote-win R]`. `--lr-floor` (fraction of `--lr`, default 0.0; **use `0.1` for curriculum**) anneals the LR toward that floor instead of 0 so a session keeps learning to its end; `--ent-coef` (default `0.01`, **use `0.03` for curriculum**) is the entropy bonus — raise it if the policy collapses to a position-blind canned action sequence instead of tracking the flame. The `make curriculum` / `make curriculum-resume` targets pass `ENT=0.03 LRFLOOR=0.1` by default. Saves the best-by-eval **policy** to `src/ai/ppo.pt` and a resumable **training checkpoint** (weights + optimizer + `iteration`/`global_step`/`best_score`/`stage_idx`) to `src/ai/ppo_ckpt.pt` (both git-ignored). `--iterations` is *per session*; `--resume` restores the checkpoint and runs that many more iterations (each session anneals its own LR — a warm restart), continuing the step/iteration counters and carrying `best_score` so a worse policy never overwrites the saved best. Bare `--resume` uses the `--checkpoint` path. `--curriculum` enables `DEFAULT_CURRICULUM` (a `(num_waves, flames_per_wave, spawn_radius)` ramp **ordered by declining achievable win rate**, from a trivially-winnable one-flame game up to the full game — each stage's comment lists the measured `greedy_clear` ceiling); the agent is promoted to the next stage once its eval win rate hits `--promote-win` (default `0.5`), and eval always runs at the current stage's difficulty. **The per-stage ceilings in the comments are `greedy_clear`'s, not PPO's** — a trained PPO policy substantially *exceeds* them (it promoted past `(3,1,1)`, greedy ceiling ~9%, and climbed the whole ramp to the full game, hitting ~65% on some shrunk stages). Use the greedy numbers only to *order* stages, not to predict PPO's reach, and don't lower `--promote-win` prematurely — with `--ent-coef 0.03` + `--lr-floor 0.1` PPO clears the `0.5` bar on every shrunk stage. The genuine wall is the **last** stage only, and only for *model-free* PPO: the full 6-wave game stays 0% for any PPO policy (the winning line is too deep for random exploration), so the curriculum's job ends at "reach stage 7", not "win it". (A lookahead **MCTS** agent, `mcts.py`, *does* win the full game — see the Winnability note above.) Best-policy score is `stage_idx * 1e6 + win_rate*1000 + mean_reward`, so a policy that reaches a harder stage always beats an easier-stage one (note: once the frontier reaches stage 7, `ppo.pt` is a full-game policy at 0% win — a lower-stage policy that actually *wins* scores lower and is overwritten). Curriculum stages are driven through `PPOConfig.curriculum` / `_VecGames.set_difficulty`; empty curriculum = one fixed full-difficulty stage (logs then omit the stage tag).
- `play.py` — `python -m src.ai.play [--policy ppo.pt] [--seed S] [--delay MS]`. Loads a policy and drives the game through the real `Renderer` (needs a display).
- `mcts.py` — **Monte-Carlo Tree Search planning agent** — the approach that actually **wins the full game** (PPO can't; see Winnability note). Exposes `mcts_action_fn(simulations, rollout_depth, c_ucb, rollout_policy, gamma, seed) -> ActionFn`, so it plugs into `evaluate`/`baselines`/`play` unchanged. It clones the live game **once per move** then runs all `simulations` on **one working game** via `Game.get_state`/`set_state` (snapshots, not per-node clones). Two design keys: (1) **shaped return** — it backs up the summed per-step `game.last_reward` (rollouts almost never win, so a win/loss leaf value is uninformative); (2) **`safe_greedy` rollout** — like `greedy_clear` but a 1-ply survival probe (step + `set_state` restore) rejects jumps that end in death, because plain `greedy_clear` suicides in ~3 steps (landing on a flame lets `attract_flames` pull a neighbour onto the player). Pure planning, **no training/network** for this version; the Phase-2 upgrade (AlphaZero-style PUCT reusing `network.py` — policy prior + value leaf replacing rollouts) is now implemented in `alphazero.py` (below). Also exposes `mcts_root_visits(game, simulations, rng, ...) -> {action: visits}` — the same search minus the final argmax, so AlphaZero can use MCTS's *visit distribution* as a policy target (see `--bootstrap-games`).
- `alphazero.py` — **AlphaZero-style PUCT search + self-play trainer** (Phase 2; see the Winnability note). Exposes `az_action_fn(net, simulations, c_puct, gamma, seed) -> ActionFn` (deterministic most-visited root action, for `evaluate`/`baselines`/`play`) and `train(AZConfig)`. The search replaces `mcts.py`'s UCB1 with **PUCT** (`Q + c_puct·P(a)·sqrt(1+ΣN)/(1+N)`, `Q` min-max normalised via `_MinMaxStats`) using the net's masked-softmax **prior** `P(a)`, and replaces the rollout with a single value-head **leaf eval** `V(s)`; backup folds the per-edge shaped rewards into the leaf value (`g = reward + gamma·g`). It clones the live game **once per move**, then expands nodes by `set_state` + `step` on one working game (snapshots, like `mcts.py`). `self_play_game` plays with root **Dirichlet noise** and visit-count sampling (temperature 1 for the first `temp_moves` plies, greedy after), recording `(obs, mask, visit-π, return-to-go)`; `train` fills a replay buffer, runs minibatch SGD (policy = cross-entropy vs visit-π, value = MSE vs return-to-go **÷ `VALUE_SCALE`=100**), evaluates via `az_action_fn`, promotes on the curriculum, and saves the best policy with `save_policy` (loadable anywhere a policy is). **`VALUE_SCALE`** normalises the value target so its loss is O(1) instead of O(10^4) and stops the value gradient from crushing the policy head (the bug that pinned the prior at uniform init — see the equal-budget box above); `_evaluate` multiplies the head's output back by `VALUE_SCALE` so the leaf value is in raw reward units for the backup. Changing it needs a retrain; old checkpoints have a differently-scaled value head. Stage tuples are unpacked as `(waves, flames, radius, formation)` with a 3-tuple tolerated (`(tuple(stage) + (None,))[:4]`), so both `DEFAULT_CURRICULUM` and `AZ_CURRICULUM` work. **`mcts_bootstrap_game(...)`** plays one game with `mcts.py` (greedy on visits, no Dirichlet) and records it as the *same* `_Sample`s self-play produces — MCTS's visit distribution as the policy target, discounted return-to-go as the value target, no network involved. `train` calls it `cfg.bootstrap_games` times at the current stage **and again on every promotion** (the buffer is a rolling window, so lines seeded for one stage are gone and wrong by the next). Off by default (`bootstrap_games=0`), and the no-bootstrap path is byte-for-byte the old behaviour. No game logic here.
- `az_train.py` — CLI for `alphazero.train`: `python -m src.ai.az_train [--iterations N] [--games-per-iter N] [--simulations N] [--eval-simulations N] [--c-puct C] [--lr] [--curriculum] [--promote-win R] [--resume [PATH]] [--out az.pt] [--checkpoint az_ckpt.pt]`. Mirrors `train.py`'s resume/curriculum/out/checkpoint conventions but uses **`AZ_CURRICULUM`** (in `train.py`): `DEFAULT_CURRICULUM`'s stages widened to 4-tuples, plus the `(1, 3, None, "line")` bridge stage before the full game — 9 stages, not 8. PPO's `DEFAULT_CURRICULUM` stays 3-tuples and untouched, because `ppo._VecGames.set_difficulty` unpacks exactly three. Saves the best policy to `src/ai/az.pt` and a resumable checkpoint to `src/ai/az_ckpt.pt` (both git-ignored). `make alphazero` / `make alphazero-resume` wrap it. **`--workers N`** (default 0 = auto, cpu−1; `1` = the historical serial path) parallelises self-play/bootstrap/eval one game per core, and **`--eval-simulations` now defaults to `--simulations`** (the gate repair — see the box above). **`--simulations 300`** (not the default 80) roughly halves the curriculum's cost. **`--bootstrap-games N [--bootstrap-simulations 300]`** seeds the replay buffer with `N` MCTS games at the current stage, re-seeding on each promotion — the lever aimed at the actual constraint (no win reaches the buffer), since MCTS wins ~50% of full games at 300 sims. The proven recipe (2026-07-10): `--curriculum --simulations 300 --bootstrap-games 8 --bootstrap-simulations 300 --iterations 100`, which reached 1/6 at equal budget and 37.5% full-game `selfplay_win` — but **only together with the `VALUE_SCALE` fix in `alphazero.py`**; without it the policy head stays at uniform init and bootstrapping alone does not lift the ceiling.

**If you change the observation layout or `ACTIONS`, no config edit is needed** — the network sizes itself from `observation_size()`/`num_actions()` at construction, but existing `ppo.pt` checkpoints become incompatible and must be retrained.
